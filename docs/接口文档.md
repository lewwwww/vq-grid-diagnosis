# 智能电网故障诊断系统 · 接口文档

> 版本：2026-09-03 ｜ 架构：BFF 三层（Nuxt 页面 → Nuxt Server → FastAPI）
> 本项目接口分**两层**，见下方说明：
> - **FastAPI 后端**（Python，端口 8000）：5 个模型推理接口，有 **Swagger 自动文档**（http://localhost:8000/docs）
> - **Nuxt Server**（Node.js/Nitro）：49 个前端接口，本文件为手动整理的 **Markdown 总览**

---

## 一、接口架构总览

```
浏览器（Nuxt 页面 index.vue）
   │ ① $fetch('/api/v1/diagnosis/batch')      相对路径 → 同源 Nuxt Server
   ▼
Nuxt Server（Nitro · Node.js）  ← 49 个接口（frontend/server/api/）
   │ ② fetch('http://localhost:8000/api/batch_diagnose')   内部转发 → FastAPI
   ▼
FastAPI（Python · :8000）  ← 5 个接口（model_inference_service.py）
      Swagger /docs 只显示这一层
```

- 前端页面**不直接**调 FastAPI（避免跨域 CORS），统一走 Nuxt Server（BFF 模式）
- Nuxt Server 负责：鉴权、参数组装、转发模型请求、把诊断结果写入 SQLite（FaultDB/AlertDB）、执行预警策略
- FastAPI 只专注模型推理，不落库、无业务逻辑

## 二、FastAPI 后端接口（5 个，Swagger 自动文档）

> 交互式文档：启动服务后访问 http://localhost:8000/docs
> 原始描述：http://localhost:8000/openapi.json

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 服务根信息 |
| GET | `/health` | 健康检查，返回 `{status:"healthy", device:"cpu"}` |
| POST | `/reload` | 热重载模型（训练出新模型后重新加载） |
| POST | `/api/diagnose` | 单条故障诊断：入参 `{device_id, features[6]}` → 返回 `fault_type / fault_type_name / confidence / encoding_indices / probabilities / inference_time_ms` |
| POST | `/api/batch_diagnose` | 批量故障诊断（**向量化批推理**）：入参 `[{device_id, features[6]}, ...]` → 返回 `{results[], total}`；单条失败不影响整批 |

**请求/响应模型（pydantic 自动生成）**：
- `DiagnosisRequest`：`device_id`(int, 必填) + `features`(array\<number\>, 必填，6 维 [Ia,Ib,Ic,Va,Vb,Vc])
- `DiagnosisResponse`：`device_id / fault_type / fault_type_name / confidence / encoding_indices / quantized_vector / probabilities / inference_time_ms / timestamp`
- 特征维度错误（≠6 维）：单条返回 400，批量中该条返回 `error` 字段

## 四、核心接口详细说明（面试重点）

### 4.1 POST /api/v1/diagnosis/batch —— 批量诊断（BFF 核心业务链）

一次请求完成"取样本 → 转发模型 → 落库 → 预警"全流程：

```
入参:  { mode: 'all'|'range'|'sampled'(默认10条), startRow?, rowCount? }
流程:  1. getStore() 取设备列表
       2. loadDiagnosisSamples*() 从 classData.csv 取样本（按 mode）
       3. 设备×样本轮转组装 modelRequests（每台设备拿一条样本的 6 维特征）
       4. 一次 fetch 转发 FastAPI POST /api/batch_diagnose（AbortSignal.timeout(15000)）
       5. 逐台设备: 写 FaultDB；if shouldCreateAlert(faultType, confidence) → AlertDB
出参:  { code, message, data: { total, success, fail, mode, sampleCount, faultTypeStats, diagnosedDevices[] } }
```

**面试可讲**：这就是 BFF 层的价值——前端只需传 `mode/startRow/rowCount`，Nuxt Server 负责调模型服务 + 业务落库 + 预警策略；而且对 FastAPI 的调用**一次批量**完成（对应后端向量化批推理优化，实测最高约 15 倍加速）。

### 4.2 GET /api/v1/diagnosis/codebook-map —— 码本映射

直接读 `../data_new/models/fault_6class/codebook_map.json` 返回给前端。前端拿到码字 → 物理语义的对照表，用于把 VQ 层输出的离散索引翻译成人话。**这就是"知识库增强问答/码本解释"的数据来源**。

### 4.3 POST /api/v1/diagnosis/import —— CSV 导入 + 自动诊断

- 支持两种 CSV 格式：**特征模式**（device_id,Ia,Ib,Ic,Va,Vb,Vc）直接使用；**运行数据模式**（device_id,voltage,current,power,temperature,load_rate）由 `generateFeaturesFromData()` 生成三相特征
- 逐条转发 FastAPI `/api/diagnose`（每条间隔 100ms 防请求过快），写 FaultDB + 按策略生成 AlertDB

### 4.4 预警策略（diagnosis-policy）

- `getFaultLevel(confidence)`：按置信度分级（阈值 30/50/80）
- `shouldCreateAlert(faultType, confidence)`：判断是否生成预警
- `createAlertRecord(device, faultType, confidence, time)`：组装预警记录
- 该策略是**纯函数**，是前端单元测试（Vitest）的候选对象

## 五、接口文档使用说明

| 层 | 文档方式 | 维护方式 |
|---|---|---|
| FastAPI（5 个） | Swagger UI `/docs` + `/openapi.json` | **自动**：改代码文档即变 |
| Nuxt Server（49 个） | 本文件 Markdown 总览 | **手动**：改 `frontend/server/api/` 后需同步本表 |

> 启动方式：
> - FastAPI：`cd algorithm && python model_inference_service.py`（端口 8000）
> - Nuxt：`cd frontend && npm run dev`（端口 3000）
> - 联调时需两个服务同时运行，Nuxt Server 通过 `MODEL_SERVICE_URL`（默认 http://localhost:8000）转发模型请求
